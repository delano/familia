## New finding

### MEDIUM — Claim leak on unpersisted-record error in instance-scoped unique-index update

**File:** `lib/familia/features/relationships/indexing/unique_index_generators.rb:369-399`, generated method `update_in_<scope>_<index_name>` (emitted for every `unique_index ... within:` declaration)

The method calls `index_hash.claim_field(new_field_value, identifier)` (line 381 — a server-side compare-and-set that immediately writes the claim) **before** calling `_ensure_persisted_before_index_write!` (line 390), which raises `Familia::PersistenceError` if the record hasn't been saved yet. If it raises, the just-taken claim on `new_field_value` is never released — there is no rescue/rollback on this path. That value becomes permanently unclaimable by any other record (it's an ownership-checked CAS keyed to this record's identifier) until someone manually calls `release_field`.

This is exactly the ordering that the sibling methods in the same file got right: the instance-scoped `add_to_*` (lines 372-382, same file) and the class-level `update_in_class_*` (`persistence.rb`, ~line 625) both check persisted-state *before* claiming, and `claim_unique_indexes!` (`persistence.rb:1095`) has explicit rollback (`release_created_index_claims!`) for precisely this failure mode. This one generated method was missed.

Not reachable through the normal auto-save flow (both guards short-circuit inside a MULTI, which is how save invokes it) — it requires a direct/manual call to `update_in_<scope>_<index>` on an unpersisted record, which is a documented part of the public generated API. No test in `try/` covers this ordering.

**Fix:** Move the `_ensure_persisted_before_index_write!` call before the `claim_field` call, matching the other three sibling methods.
