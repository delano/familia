## Historical finding

### MEDIUM — Claim leak on unpersisted-record error in instance-scoped unique-index update — Resolved

**Affected code at audit time:** generated method
`update_in_<scope>_<index_name>` in
`lib/familia/features/relationships/indexing/unique_index_generators.rb`
(emitted for every `unique_index ... within:` declaration).

At audit time, the method called
`index_hash.claim_field(new_field_value, identifier)`—a server-side
compare-and-set that immediately writes the claim—**before** calling
`_ensure_persisted_before_index_write!`, which raises
`Familia::PersistenceError` if the record has not been saved yet. If it raises, the just-taken claim on `new_field_value` is never released — there is no rescue/rollback on this path. That value becomes permanently unclaimable by any other record (it's an ownership-checked CAS keyed to this record's identifier) until someone manually calls `release_field`.

At audit time, the sibling methods used the safe ordering: the instance-scoped
`add_to_*` and class-level `update_in_class_*` methods checked persisted state
_before_ claiming, and `claim_unique_indexes!` had explicit rollback
(`release_created_index_claims!`) for this failure mode. This generated method
was missed.

The normal auto-save flow did not reach this path because both guards
short-circuit inside its MULTI. It required a direct call to
`update_in_<scope>_<index>` on an unpersisted record, which is part of the
public generated API. No `try/` test covered this ordering at audit time.

**Resolution:** `_ensure_persisted_before_index_write!` now runs before
`claim_field`, matching the sibling methods. Regression coverage verifies that
the rejected call leaves no claim behind.
