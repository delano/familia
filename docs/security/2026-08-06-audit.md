## Finding

### MEDIUM — `Lock#acquire(ttl: nil)` has conflicting expiration semantics and an unsafe inherited-TTL path — Open

**Files:** `lib/familia/data_type/types/lock.rb`,
`lib/familia/data_type/types/stringkey.rb`, and `lib/familia/data_type.rb`

The public `Lock#acquire` documentation and standalone lock tryout define
`ttl: nil` as no expiration. The implementation instead delegates that branch
to `StringKey#setnx`. That method issues `SETNX` and then separately calls
`update_expiration`. For a related lock without its own expiration option,
`DataType#default_expiration` can inherit a positive `default_expiration` from
the parent Horreum.

The result has three defects, depending on the intended contract:

- If `ttl: nil` means no expiration, a related lock can expire unexpectedly
  when its parent has a default expiration. A long-running holder can then lose
  mutual exclusion while it still believes it owns the lock.
- `StringKey#setnx` calls `update_expiration` regardless of whether `SETNX`
  succeeds. A failed nil-TTL acquisition can therefore replace or extend the
  existing owner's TTL even though the caller did not acquire the lock.
- If `ttl: nil` is intended to inherit the relation or parent expiration, the
  effective TTL is attached with a second Redis command. A process or
  connection failure after `SETNX` succeeds but before `EXPIRE` lands leaves a
  lock without the intended TTL. It then persists until the holder releases it
  or an operator removes it.

The explicit positive-TTL path does not have this gap: since `5ec8819`, it uses
one atomic `SET NX EX` command. At the current verification commit, the
nil-TTL path and its tests are unchanged from the original audit snapshot, so
the finding remains open.

**Recommendation:** Choose and document one `ttl: nil` contract. If it means no
expiration, issue `SET NX` directly and bypass the generic expiration hook. If
it means inherit the effective default, resolve that value before writing and
use `SET NX EX <ttl>` when positive or `SET NX` when absent/zero. Either form
must leave an existing lock and its TTL unchanged when `NX` fails. Add coverage
for successful and contended acquisition of a related lock whose parent has a
positive `default_expiration`.

  paths had no seconds/milliseconds confusion, 30-day ceiling, or truncation.

  same `ScoreEncoding.permission_level_value` function used by permission
  checks. The reviewed pagination retained permission filtering.
- **General secret/CAS/race scan.** Within `91480ec..c7eb1a1`, the audit found no
  newly introduced hardcoded secrets, non-constant-time secret comparisons,
  unsafe `Marshal.load` or `YAML.load`, externally controlled internal `send`
  targets, claim-compensation regression, or non-atomic capped-collection
  write/trim sequence. This statement has not been extended to later commits.

## Close calls ruled out at audit time

- `claim_unique_<index_name>!` intentionally claims before persistence because
  it is the class-level primitive used during create/save, before the record
  hash exists; it is not the update-existing-record path fixed after the prior
  audit.
- `Manager#decrypt` intentionally walks explicit historical salt or
  personalization candidates so old ciphertext remains readable; the
  fail-closed active-key change applies to encryption.
- `extend_expiration` remains a read/compute/write sequence. Concurrent extends
  can lose a TTL update, but the reviewed path does not create the lock
  ownership failure described above.

## Validation limits

The current verification compared the relevant source paths between `c7eb1a1`
and `d2bd2313`, inspected the current API documentation and tryouts, and
reproduced both behaviors against the configured Valkey test service. A
successful related-lock acquisition with `ttl: nil` received the parent's
30-second TTL through separate `SETNX` and `EXPIRE` commands. A failed
acquisition against a lock with 120 seconds remaining returned `false` but
replaced the owner's TTL with the parent's 30-second default. The existing lock
and expiration-cascade tryouts passed (34 and 17 testcases), but neither covers
this combination.
